# Проблема и метрики

Файл ведёт OpenCode. Обсудите с агентом содержание и проверьте предложенный diff. Все дополнения и исправления поручайте агенту в чате.

## Проблема

- Пользователь: студент-инженер и/или интегратор CI, который вызывает API для автоматизированного code review по diff.
- Ситуация: нужно принять строковый diff и получить структурированный комментарий, пригодный для документации и последующей автоматизации.
- Что происходит сейчас: эндпойнт принимает произвольный dict без схемы, обращается к payload["diff"]; нет валидации, лимитов размера и обработки ошибок; сервис формирует промпт без ограничений.
- Почему это мешает пользователю или бизнесу: ошибки 500 при некорректном входе, непредсказуемая OpenAPI-схема, возможные падения/зависания при больших diff, слабая воспроизводимость и документируемость результата.
- Что не входит в задачу: реализация и выбор конкретной схемы аутентификации; замена LLM-клиента; построение полноценного UI.

## Метрики

Обсудите с OpenCode показатели, по которым можно проверить решение проблемы. Агент записывает согласованный способ замера и ожидаемое изменение для каждого показателя.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля 2xx на корректном входе | Бейзлайн измерение на тестовом наборе | >= 99% | Перед релизом и на каждой сборке | Интеграционные тесты |
| Доля 4xx на некорректном входе | Бейзлайн: 500 при отсутствующем ключе diff | 100% 4xx (422 или 413) | Перед релизом и на каждой сборке | Интеграционные тесты |
| Ограничение по размеру diff | Нет явного лимита | Введен лимит, например 64 KB | На этапе валидации | Юнит и интеграционные тесты |
| SLA по времени ответа | Не определен | P50 <= 2s, P95 <= 5s на тестовом наборе | На CI стенде | Нагрузочные тесты |

## Почему изменение метрики подтвердит решение проблемы

- Если корректные запросы дают 2xx, а некорректные стабильно маппятся в 4xx, значит валидация и обработка ошибок работают и пользователи не получают 500.
- Лимит на размер diff предотвращает переполнение контекста LLM и отказ в обслуживании, что отражается в стабильности и SLA.
- SLA по времени ответа подтверждает, что синхронный путь или стратегия исполнения соответствует ожиданиям пользователей.
## Как использовали AI

- Для чего: сформулировать проблему пользователя и измеримые метрики, связанные с качеством и надежностью API ревью.
- Тип промпта: zero-shot (baseline) и master prompt (структурированный вывод с evidence).
- Строка в [`prompts.md`](prompts.md): P1-01, P1-02 и раздел «Сравнение двух запусков».
- Что проверил студент и какие исправления поручил агенту: подтвердили риски и метрики цитатами из TRAINING_PR.diff; уточнили границы задачи (без auth/UI), задали цели по 2xx/4xx, лимиту размера и SLA.
