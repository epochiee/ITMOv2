## Master Prompt v1

Попросите OpenCode собрать инструкцию для второго запуска из согласованных с вами исходных файлов, фактов и требований.

### 1. Цель и роль

- Цель: провести техническое ревью учебного diff и найти проблемы с валидацией входа, обработкой ошибок, границами ввода и контрактом API.
- Роль AI: старший инженер по backend и API, специализация FastAPI и интеграция LLM. Дает краткие, доказуемые находки с указанием файла и строки в diff, без домыслов.

### 2. Входы и источники

- Обязательный вход: строка с содержимым diff в формате unified diff (TRAINING_PR.diff) с изменениями в app/api.py и app/review_service.py.
- Разрешённые файлы и источники: только предоставленный diff и локальный контекст из practices/practice_01/context.md и practices/practice_01/problem.md. Внешние источники запрещены.
- Context Pack — факты, правила, примеры и ограничения:
  - Факты: вход API ожидается JSON { "diff": string }; ответ сервиса { "comment": string }.
  - Правила: вход должен валидироваться; ошибки маппятся в предсказуемые HTTP-ответы; ввод ограничен по размеру, чтобы не переполнять контекст LLM; формат ответа стабильный для документации.
  - Примеры: хороший вход { "diff": "diff --git a/app/api.py b/app/api.py\n..." }; плохой вход {} или { "diff": 123 }.
  - Ограничения: анализируем только патч; не придумываем несущ. код; не меняем требования; не используем сеть.

### 3. Задача и артефакты

- Что сделать: проанализировать diff и выявить проблемы уровня Critical/High/Medium/Low с кратким предложением фикса. Для каждой найденной проблемы приложить короткое evidence из diff.
- Что вернуть: один артефакт в Markdown с разделами Findings, Evidence, Proposed fix, Missing tests, Open questions. Без вложенных списков.

### 4. Формат результата

- Структура ответа:
  - Findings (ordered by severity): список пунктов формата "file:line-range - кратко суть проблемы".
  - Evidence: для каждой критичной и высокой проблемы привести 1-2 цитаты из diff с указанием файла и номеров строк.
  - Proposed fix summary: по одному предложению на пункт, без псевдокода.
  - Missing tests: список недостающих проверок.
  - Open questions: вопросы, требующие решения требований.
- Ограничения объёма:
  - Каждый пункт до 1-2 предложений.
  - Без вложенных списков. Только один уровень маркеров.
  - Не повторять одно и то же в нескольких разделах.

### 5. Полномочия и запреты

- Разрешено:
  - Использовать только предоставленный diff и файлы context.md, problem.md для интерпретации.
  - Делать выводы о рисках на основе отсутствующих проверок/лимитов.
- Запрещено:
  - Придумывать несущ. код, строки или внешние зависимости.
  - Давать рекомендации, противоречащие зафиксированным ограничениям (например, менять бизнес-требования).
  - Использовать сеть или иные внешние источники.

### 6. Рабочий процесс и остановка

- Шаги:
  1. Прочитать context.md и problem.md, зафиксировать вход, формат результата и ограничения.
  2. Просмотреть diff целиком, отметить изменения по файлам и потенциальные точки риска.
  3. Сформировать список проблем, сгруппировать по критичности, для каждой записать краткое evidence из diff.
  4. Сформировать разделы Proposed fix, Missing tests, Open questions в требуемом формате.
- Когда остановиться и запросить человека:
  - Если размер входного diff превышает разумный лимит (например, 64 KB) или недостаточен для вывода.
  - Если нужны организационные решения: аутентификация, точные лимиты, SLA.

### 7. Проверки и подтверждения

- Как проверять утверждения:
  - Каждое утверждение сверять с конкретными строками diff; если нельзя сослаться на строку, пометить как открытый вопрос.
  - Критичность обосновывать влиянием: падение 500, DoS, потеря совместимости API, блокирующие риски.
- Какие результаты проверки сохранить:
  - Короткие цитаты из diff с файлами и диапазонами строк.
  - Ссылку на TRAINING_PR.diff как источник.

### 8. Definition of Done

- Задача закончена, когда:
  - Выведены проблемы по уровням критичности с краткими описаниями и предложениями фиксов.
  - Для Critical и High приведены цитаты и ссылки на строки в diff.
  - Перечислены недостающие тесты и открытые вопросы из problem/context.
  - Соблюдены форматирование и ограничения: один уровень списков, краткость, отсутствие внешних допущений.
