# Анализ процесса: AS IS и TO BE

Файл ведёт OpenCode. Обсудите с агентом содержание и проверьте предложенный diff. Все дополнения и исправления поручайте агенту в чате.

## AS IS

Расскажите OpenCode о текущем процессе. Попросите агента описать участников, задержки, ручные операции и точки потери информации.

Сценарий: разработчик или CI отправляет POST /api/reviews с JSON, сервис возвращает комментарий LLM.

Участники и шаги:
- Клиент отправляет JSON без строгой схемы.
- Эндпойнт create_review(payload: dict) обращается к payload["diff"] без проверки.
- При отсутствии ключа diff возникает KeyError и 500.
- ReviewService.review формирует промпт из всего diff без лимитов и вызывает llm.generate.
- Ответ возвращается как {"comment": answer} без явной модели.

Точки задержек и ошибки:
- Долгий вызов LLM блокирует поток выполнения (sync handler в threadpool).
- Большие diff могут переполнить контекст LLM и вызвать сбои.
- Нет валидации входа, нет ограничений и маппинга ошибок в предсказуемые статусы.

## TO BE

Процесс с валидацией, лимитом размера и контролем ошибок.

```mermaid
flowchart LR
    A[Клиент: POST /api/reviews\nJSON {diff}] --> V{Валидация}
    V -- 422 --> E1[Ошибка валидации]
    V -- 413 --> E2[Слишком большой diff]
    V -- OK --> S[ReviewService.review]
    S --> P[Сбор промпта]
    P --> L[LLM.generate]
    L -- Ошибка --> E3[502/503 LLM error]
    L -- Ответ --> R[JSON {comment}]
```

## Разница

| Что меняется | AS IS | TO BE | Как проверим изменение |
|---|---|---|---|
| Валидация входа | Отсутствует | Pydantic-модель, 422 на невалидный вход | Интеграционные тесты 422 |
| Лимит размера diff | Нет | Лимит, например 64 KB, 413 при превышении | Тест превышения лимита |
| Контроль ошибок LLM | Нет | try/except и маппинг 502/503 | Интеграционные тесты ошибок |
| Контракт API | Голые dict | Явные модели запроса/ответа | Проверка OpenAPI и e2e |
| Производительность | Потенциальные блокировки | SLA P50/P95 в пределах | Нагрузочные тесты |

## Как использовали AI

- Для чего: анализ diff, фиксация AS IS и проектирование TO BE для безопасного API ревью.
- Тип промпта: zero-shot для baseline и master prompt для доказательного результата.
- Строка в prompts.md: P1-01 и P1-02, раздел Master Prompt v1 и Сравнение двух запусков.
- Что проверил студент и какие исправления поручил агенту: сопоставили Findings с цитатами из TRAINING_PR.diff, добавили валидацию, лимиты и контроль ошибок в дизайн.
