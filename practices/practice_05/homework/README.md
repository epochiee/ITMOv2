# ДЗ 5. Две команды — одна фича (GitHub Spec Kit)

**Фича:** локальный сервис предпросмотра changelog `changelog-gen-web`. Страница, на которой указываешь диапазон и типы, видишь готовую секцию (та же, что у CLI) и копируешь её.
**Фреймворк:** GitHub Spec Kit `specify-cli 1.2.4.dev0` (`uv tool install specify-cli --from git+https://github.com/github/spec-kit.git`), интеграция `claude`, скрипты `sh`.
**Команды:** два отдельных агента-чата. Команда 1 писала спеку UI, команда 2 — спеку логики. До согласования они не видели работу друг друга.

## Запуск демо

```bash
make -C practices/practice_05 install
cd <любой git-репозиторий>
<путь>/practices/practice_05/changelog-gen/.venv/Scripts/changelog-gen-web --port 8765
# открыть http://127.0.0.1:8765/
```

Сценарий на 2 минуты:

1. «Показать» — секция, равная `changelog-gen`.
2. «Ничего» → `feat` → «Показать» — breaking-коммит остаётся.
3. В поле `--output=x` → ошибка у поля, файл не создан.
4. `v9.9..HEAD` → «Не удалось найти…».
5. Остановить сервис → «Нет связи» → запустить → «Повторить».

## Сравнение с OpenSpec (на одном и том же проекте)

| | OpenSpec 1.14.1 (часть 1–2 практики) | Spec Kit 1.2.4.dev0 (ДЗ) |
|---|---|---|
| Единица работы | **change** — дельта к живой спеке (`ADDED / MODIFIED / REMOVED`), после archive вливается в `openspec/specs/` | **feature** — каталог `specs/NNN-name/` со спекой, планом и задачами; живой «главной» спеки нет, фичи копятся рядом |
| Brownfield | сильная сторона: `MODIFIED` требует скопировать требование целиком — так нашлось противоречие с прежним поведением (`write-changelog-file` меняет требование про stdout) | спека пишется «с нуля» про фичу; связь с существующим поведением держится текстом («совпадает с CLI») и конституцией |
| Артефакты | proposal → specs → design (условный) → tasks; лёгкие, 1–2 страницы | spec (истории P1–P3, FR, SC, чеклист качества) → plan (+research, quickstart, contracts) → tasks по историям; объём в 3–4 раза больше |
| Проверка | `openspec validate --strict` — структура (SHALL/MUST, сценарии `####`); детерминированно, без LLM | чеклист качества заполняет сама модель; детерминированной проверки формы нет |
| Правила проекта | `config.yaml: context + rules.<artifact>` — точечно на артефакт; проверено, что правило приходит в `instructions` | `constitution.md` — принципы и gate «Constitution Check» в каждом plan; шире, но соблюдение проверяет только модель |
| Состояние | несколько активных changes параллельно, CLI различает по имени | одна «текущая» фича в `.specify/feature.json`: для двух параллельных команд пришлось задать каталоги явно и запретить им писать этот файл |
| Контракт между командами | нет отдельного артефакта: пришлось бы держать в design | `contracts/` в plan, но в пределах одной фичи. Общий контракт двух фич положили в `specs/contracts/` по собственной договорённости |
| Где сильнее | эволюция существующего поведения, archive и история, строгая форма | новая фича с UX: приоритизированные истории, измеримые SC, явная граница «что / как» |

Вывод: для изменений поведения CLI удобнее OpenSpec (дельты, archive, `validate`). Для новой фичи из двух частей, которые согласуют разные люди, — Spec Kit с отдельным контрактом. Принцип «один источник истины на стыке» обеспечил не фреймворк, а решение вынести контракт в отдельный файл и заменить им разделы «ожиданий» в обеих спеках.

## Рефлексия

**Что согласовали.** Из 13 решений 5 — настоящие конфликты:

- коды ошибок (5 имён UI против 10 у логики);
- пустой репозиторий: ошибка или пустой результат;
- debounce: нужен ли автозапрос;
- `range_too_large`, о котором UI не знал;
- имя репозитория, которого не было в справочнике.

Ещё 5 — маркеры NEEDS CLARIFICATION; все закрыты отказом от расширения: заголовок версии, подсказки тегов, структурированный список коммитов. Пустой репозиторий решён в пользу UI. Пользователю непонятно, почему свежий репозиторий — «ошибка», а для логики это одна проверка `rev-parse --verify HEAD`.

**Что сработало.**

- **Раздел «ожидания от другой стороны» в каждой спеке.** Без него расхождения всплыли бы только в коде: например, UI ждал коды `range_not_found` / `repo_unavailable`, а логика отдавала бы `unknown_range` / `not_a_repository`.
- **Команда логики проверила гипотезу запуском.** Она нашла вторую дыру, которую я не знал: строка `README` в диапазоне git трактует как путь. Отсюда `--end-of-options RANGE --`.
- **Сквозной тест «API = CLI побайтно» + общий `core.py`.** Расхождение фильтра CLI и сервиса невозможно по построению, а 41 старый тест CLI прошёл после переноса логики без единой правки.

**Где пришлось вмешаться человеку (агенту основного чата).**

- **Протокол согласования** — обе команды «честно» описали свой мир, сводить пришлось вручную.
- **Параллельная работа в Spec Kit.** `feature.json` и автонумерация фич рассчитаны на одного автора.
- **Две ошибки UI нашлись только в браузере**, тестами pytest не ловятся. Первая: пометка «Параметры изменены» после пустого результата. Вторая: «4 коммитов».

**Чему научился.** Спека важна не сама по себе, а тем, что заставляет записать предположение до кода, где его дёшево опровергнуть. Самые ценные строки во всех спеках — разделы «Ожидания от …» и NEEDS CLARIFICATION, а не FR-списки.
