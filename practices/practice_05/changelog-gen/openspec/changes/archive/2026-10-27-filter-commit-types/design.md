# Design

## Context

Мотивация — в `proposal.md` (раздел Why), требования — в `specs/changelog-cli/spec.md`.

Сейчас `cli.main()` берёт `sys.argv[1]` без разбора аргументов и передаёт его в `git log`. Конвейер: `read_messages()` → `parse_commit()` → `render()`. Допустимые типы уже перечислены в `parser.TYPES`. `main()` не покрыт тестами: тестируется только `read_messages()`.

## Goals / Non-Goals

**Goals:**
- Фильтр встраивается между разбором и рендером, не меняя `parser` и `renderer`.
- Проверка `--types` выполняется до вызова `git`.
- `main()` можно вызвать из теста со своим списком аргументов.

**Non-Goals:**
- Не выносим фильтр в отдельный модуль и не делаем его публичным API для MCP-сервера.
- Не меняем обработку ошибок `git` (неверный диапазон).

## Decisions

1. **`argparse` вместо ручного `sys.argv`, с `allow_abbrev=False`.** Даёт `--help`, код 2 и `usage:` при ошибках использования без своего кода. Сокращения отключены, иначе `--type` и `--t` молча работали бы как `--types`. Альтернатива — ручной разбор `sys.argv`: меньше изменений, но пришлось бы самим писать сообщения об ошибках и `--help`. `argparse` есть в стандартной библиотеке, новая зависимость не нужна.
2. **Проверка значения через `type=` у аргумента `--types`, повтор через `action="append"`.** Функция разбирает строку, обрезает пробелы и сверяет каждое значение с `parser.TYPES`; при ошибке бросает `argparse.ArgumentTypeError`. Тогда `argparse` сам печатает сообщение и выходит с кодом 2 ещё до чтения истории. Результаты повторов объединяются в одно множество. Альтернатива — проверка после `parse_args()` с ручным `sys.exit(2)`: дублирует поведение `argparse`.
3. **Фильтр по объекту `Commit` после разбора.** Условие: `commit.breaking or commit.type in types`. Фильтр по строке сообщения потребовал бы второго регулярного выражения, а `AGENTS.md` это запрещает.
4. **`main(argv: list[str] | None = None)`.** `None` означает `sys.argv[1:]` (поведение консольного скрипта не меняется), список — для тестов. Тесты вызывают `main()` в `tmp_path` с собственным git-репозиторием, как уже делает `test_read_messages_keeps_body`. Ошибки использования `argparse` приходят в тест как `SystemExit` с кодом 2, а не как возвращаемое значение: тесты проверяют `excinfo.value.code`. Отсутствие трейсбека проверяет один сквозной тест через `subprocess` (`python -m changelog_gen.cli --foo`). То, что git не вызывается при неверном `--types`, проверяется подменой `cli.read_messages` через `monkeypatch`.
5. **Характеризационный тест до рефакторинга.** Перед заменой разбора аргументов фиксируем точный stdout и строки `skip:` текущего `main()` на временной истории. Тест проходит на старом коде и без изменения ожиданий — на новом. Это и есть эталон для сценария «Без флага вывод не меняется».

## Risks / Trade-offs

- [Раньше лишние аргументы молча игнорировались, а флаги git (`--no-merges`, `--since=…`) недокументированно работали; теперь это код 2] → Указано в proposal как **BREAKING**; документированный вызов (`changelog-gen [RANGE]`) работает как прежде.
- [Диапазон, начинающийся с `-`, `argparse` примет за флаг] → Диапазоны git так не начинаются; при необходимости работает `changelog-gen -- RANGE`. Исключение: `-3` `argparse` считает числом и передаёт как диапазон, это совпадает со старым поведением.
- [Через `changelog-gen -- --output=x` значение по-прежнему уходит в `git log` как опция и может записать файл] → Для локального CLI риск низкий: пользователь запускает его на своей машине. В это изменение не берём. Для сетевого ввода (веб-сервис) защита обязательна и описывается там.
- [Breaking-коммит неотобранного типа появляется в выводе неожиданно для пользователя] → Поведение описано в спецификации и `--help`; это осознанный выбор в пользу того, чтобы не скрывать ломающие изменения.
