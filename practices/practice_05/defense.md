## 2. Теория: Spec-Driven Development

### 2.1 Что это и зачем

**SDD (spec-driven development)** — подход, при котором до кода записывается **спецификация**: что система должна делать, при каких условиях, какие ошибки, что не входит в изменение. Спека — источник истины, код — её реализация, тесты — проверка соответствия.

Зачем это при работе с AI-агентом:

- **Агент быстро пишет код, но плохо держит намерение.** Без спеки он «угадывает» требования и расширяет границы. Спека делает намерение и границы **видимыми** до того, как написан код (слайд 2).
- **Дешевле ошибиться на бумаге.** Пробел в спеке правится за минуту; тот же пробел в коде — это переписывание и тесты.
- **Проверяемость.** Каждый сценарий спеки — готовый тест. «Готово» = все сценарии подтверждены, а не «агент сказал, что готово».
- **Разделение ролей** (слайд 3):
  - **Человек** задаёт цель и принимает итог.
  - **Модель** пишет текст и код.
  - **CLI и раннер тестов** делают детерминированные проверки, без LLM.

### 2.2 Общий цикл (слайд 2)

```
Explore → Propose → Human review → Apply → Tests / acceptance → Sync / Archive
   ^                                   |
   +---- ошибка или новое понимание ---+   (возвращаемся к решению, правим спеку, а не «чиним в коде»)
```

Ключевая мысль: если на этапе кода выяснилось, что спека неверна, **останавливаем код и правим спеку** (`/opsx:update`), а не «тихо» меняем поведение.

### 2.3 Greenfield и brownfield

- **Greenfield** — новый проект, спеку пишем с нуля.
- **Brownfield** — существующий код без спек (наш случай). Сложность в том, что у старого кода есть **неявное поведение**, на которое кто-то полагается. Поэтому в brownfield важно:
  - на explore записать, **что сохраняем**;
  - до рефакторинга зафиксировать текущее поведение **характеризационным тестом** (см. 4.1);
  - явно пометить ломающие изменения (**BREAKING**).

## 3. Теория: OpenSpec

### 3.1 Модель данных

```
openspec/
├── config.yaml               # контекст проекта и правила для артефактов
├── specs/                    # ТЕКУЩЕЕ поведение системы (source of truth)
│   └── changelog-cli/spec.md #   одна capability = одна папка
└── changes/                  # изменения «в полёте»
    ├── write-changelog-file/ #   активный change: proposal, specs (дельта), design, tasks
    └── archive/
        └── 2026-10-27-filter-commit-types/   # завершённый change — история
```

- **Capability** — устойчивая область поведения (у нас `changelog-cli`). Называется по поведению, а не по задаче: `changelog-cli`, а не `add-types-flag`.
- **Change** — одно изменение. В нём **дельта** к спекам, а не копия спеки.
- **Main spec** (`openspec/specs/`) — как система работает сейчас. Пока не было первого archive, список пуст, и это нормально (слайд 8).

### 3.2 Артефакты change (схема `spec-driven`)

| Артефакт | Вопрос | Содержание |
|---|---|---|
| `proposal.md` | **Зачем и что** | Why, What Changes (с пометкой **BREAKING**), Capabilities (new/modified), Impact, «не входит» |
| `specs/<cap>/spec.md` | **Что система должна делать** (дельта) | `## ADDED / MODIFIED / REMOVED / RENAMED Requirements`; требования с SHALL/MUST и сценарии WHEN/THEN |
| `design.md` | **Как** (условный, создаётся не всегда) | Context, Goals/Non-Goals, Decisions с альтернативами, Risks → Mitigation |
| `tasks.md` | **Шаги** | Чекбоксы `- [ ] 1.1 …`, у каждого — способ проверки |

Граф зависимостей (видно в `openspec status --json`): `proposal → specs, design → tasks`. Для apply нужен `tasks` (`applyRequires: ["tasks"]`).

**Когда нужен design** (из инструкции схемы): изменение затрагивает несколько модулей, есть новая зависимость, безопасность или миграция, неоднозначность, которую лучше снять до кода. Поэтому правило части 2 действует «для будущих design, design нужен не всегда» (слайд 14).

### 3.3 Формат требований (то, что проверяет `validate --strict`)

```markdown
### Requirement: Проверка значения --types
Если `--types` содержит неизвестный тип ..., CLI MUST завершиться с кодом 2 ...

#### Scenario: Опечатка в типе
- **WHEN** пользователь запускает `changelog-gen --types feat,feature`
- **THEN** код завершения 2
- **AND** stdout пуст
```

Правила:

- В тексте требования MUST/SHALL. Мы писали по-русски, но ключевые слова оставили английскими — так задано в `context` config.yaml.
- У каждого требования **минимум один сценарий**. Заголовок сценария — ровно `####`: с `###` или списком он «молча» не распознаётся.
- Описание требования — не длиннее 500 символов, иначе `--strict` падает. Одно поведение — одно требование.
- У новой capability первый раздел — `## Purpose` (≥ 50 символов); при archive он переносится в main spec.
- **MODIFIED** копирует блок требования **целиком**, со всеми сценариями. Иначе при archive детали потеряются, а `validate` отклонит блок без существующего сценария.
- Change без дельт отклоняется, если в `.openspec.yaml` не указано `skip_specs: true` (для чистого рефакторинга).

### 3.4 Workflow профиля `core` (6 штук)

| Workflow | Claude Code / OpenCode / Codex | Что делает | Граница |
|---|---|---|---|
| explore | `/opsx:explore` · `/opsx-explore` · `$openspec-explore` | «Партнёр по размышлению»: читает код, задаёт вопросы, рисует схемы | **Не пишет код и не меняет config** |
| propose | `/opsx:propose` · `$openspec-propose` | Создаёт change и все артефакты по `instructions` | **Только планирование, стоп до apply** |
| update | `/opsx:update` · `$openspec-update-change` | Правит артефакты и держит их согласованными | **Никогда не трогает код** |
| apply | `/opsx:apply` · `$openspec-apply-change` | Идёт по `tasks.md`, отмечает `[x]` | Пауза, если спека неверна или нужна работа вне задач |
| sync | `/opsx:sync` · `$openspec-sync-specs` | Сливает дельту в main spec, change остаётся активным | — |
| archive | `/opsx:archive` · `$openspec-archive-change` | Проверяет задачи и sync, переносит change в `archive/YYYY-MM-DD-name` | Только после приёмки |

Ещё 6 workflow доступны через `openspec config profile`: new, continue, ff, bulk-archive, verify, onboard.

**Sync или archive:** sync обновляет main spec, но change остаётся активным. Archive фиксирует итог и переносит change в историю (перед этим проверяет, что sync сделан).

### 3.5 CLI: что делает OpenSpec, а что модель (слайд 3)

Сам CLI **не вызывает LLM**. Он:

- `list` / `list --specs` — какие changes и capabilities есть;
- `show X --type change|spec` — показать артефакт или спеку;
- `status --change X --json` — граф артефактов (что готово, что заблокировано);
- `instructions <artifact> --change X --json` — **собирает инструкцию для модели**: шаблон, указания схемы, `context` и `rules` из config, путь вывода, зависимости;
- `validate X --strict` — детерминированная проверка **структуры**, не смысла;
- `view` — разовый текстовый дашборд.

Модель (в coding client) читает инструкцию и **пишет** текст и код. Человек **принимает**.

### 3.6 `openspec/config.yaml`

```yaml
schema: spec-driven
context: |              # фон проекта: попадает в instructions каждого артефакта
  Language: ru
  ...
rules:                  # правила по артефактам: только для указанного артефакта
  design:
    - Объясни взаимодействие диаграммой Mermaid.
```

- `context` и `rules` — **ограничения для модели**, в артефакт их не копируют.
- `rules.<artifact>` приходит только в инструкции этого артефакта. Мы проверили: в `instructions design` правило есть, в `instructions specs` — `rules: None`.
- Правило действует на **будущие** артефакты. Уже написанные артефакты оно само не меняет — их надо обновить через `/opsx:update`, что и было сделано на шаге 8.
- Второй ключ `rules:` создавать нельзя: в YAML второй ключ молча перезапишет первый. Поэтому на слайде сказано «дополните текущий rules».
- Есть ещё `operations.apply/archive.guidance` — необязательные советы для выполнения workflow (мы не использовали).

## 4. Теория: остальное, что всплывёт в вопросах

### 4.1 Характеризационный тест

Термин Майкла Физерса («Working Effectively with Legacy Code»). Это тест, который фиксирует **текущее** поведение кода — каким бы оно ни было, — **до** рефакторинга. Он должен проходить на старом коде и без изменения ожиданий на новом. Так «поведение не изменилось» доказывается, а не утверждается. У нас: `test_main_without_arguments_keeps_output` (задача 1.0). Проверяющий подтвердил, что на старом коде он проходит, а новые тесты падают.

### 4.2 Независимая проверка

Слайд 11: «Не считай отчёт автора самостоятельной проверкой». Автор (и агент-автор) склонен подтверждать свою работу. Проверяющий — отдельный контекст без истории основного чата, файлы не меняет, по каждому сценарию даёт «ожидание → факт → доказательство».

### 4.3 argparse (часть 1)

- Ошибка использования — **код 2**, сообщение `usage:` в stderr. В тесте это не возврат функции, а `SystemExit(2)`.
- `allow_abbrev=True` по умолчанию: `--type` и `--t` сработали бы как `--types`. Поэтому `allow_abbrev=False`.
- `type=функция` проверяет значение до выполнения программы: при `ArgumentTypeError` argparse сам печатает ошибку и выходит с кодом 2, **git не вызывается**.
- `action="append"` позволяет повторять флаг; повторы объединяем.

### 4.4 Безопасность (ДЗ)

- **Option injection (внедрение опций).** `git log` принимает опции из аргумента: `--output=x` пишет файл. Защита — проверка «не начинается с `-`» и `git log ... --end-of-options RANGE --`. `--end-of-options` запрещает трактовать дальше опции, завершающий `--` — пути. Команда 2 нашла, что без `--` строка `README` трактуется как путь к файлу.
- **DNS rebinding.** Злонамеренный сайт перепривязывает свой домен на `127.0.0.1`, и JS со страницы этого сайта начинает ходить в локальный сервис. Защита: сервис принимает только `Host: 127.0.0.1:<порт>` или `localhost:<порт>`, иначе 403. CORS не включаем.
- **Bind только на `127.0.0.1`** — сервис недоступен из сети.
- **XSS.** Текст changelog выводится через `textContent`, нигде не `innerHTML`. Сообщение коммита `preview <changelog> & copy` показывается буквально. Тест проверяет, что `innerHTML` в странице нет.
- **Не отдавать внутренности.** Ошибки — код и детали по контракту, без трейсбеков, абсолютных путей и сырого вывода git.
- **Windows: `SO_REUSEADDR`** позволяет второму серверу молча занять тот же порт, поэтому на win32 он выключен.

### 4.5 Атомарная запись (design фичи `--output`, часть 2)

Пишем во временный файл в том же каталоге, затем `os.replace` (атомарно в пределах одной ФС). При сбое целевой `CHANGELOG.md` не портится. Альтернатива «писать сразу в файл» при сбое оставляет его обрезанным.

### 4.6 GitHub Spec Kit (ДЗ)

| Шаг | Команда | Артефакт |
|---|---|---|
| Принципы проекта | `/speckit-constitution` | `.specify/memory/constitution.md` — неизменяемые принципы, версия (semver) |
| Спека | `/speckit-specify` | `specs/NNN-name/spec.md`: истории P1–P3 (каждая — независимо тестируемый MVP), FR-xxx, SC (измеримые), Assumptions; **не более 3** маркеров `[NEEDS CLARIFICATION]`; чеклист качества `checklists/requirements.md` |

- Git-ветки создаются только расширением `git`; мы его не подключали.

### 4.7 OpenSpec и Spec Kit — главное отличие

- **OpenSpec** живёт **дельтами к живой спеке**: удобно развивать существующее поведение. В brownfield это сильная сторона. Есть `validate` и archive с историей.
- **Spec Kit** живёт **фичами**: удобно спроектировать новое с UX, приоритетами и измеримыми критериями. Живой «главной» спеки нет. Правила проекта — конституция с gate в каждом плане.

### Шаг 1. Explore (слайд 6) → `evidence/01-explore.md`

Промпт: «Хочу фильтр по типам коммитов: `changelog-gen --types feat,fix`. Прочитай затронутый код и тесты. Что есть? Что спорно? Найди команду проверки, запусти baseline. Предложи границы и вопросы. Код не меняй.»

Что нашёл:

- `cli.main()` берёт `sys.argv[1]` и целиком отдаёт в `git log`, поэтому `changelog-gen --types feat` → трейсбек `CalledProcessError`.
- Допустимые типы уже есть в `parser.TYPES`: второй список не нужен.
- `main()` не покрыт тестами.

Спорные места и решения:

- **Breaking-коммит неотобранного типа** — оставлять всегда, как в пресетах conventional-changelog. Иначе фильтр скроет ломающее изменение.
- **Неверный тип** — ошибка с кодом 2, а не тихий игнор: опечатка дала бы пустой changelog.
- **Переход на argparse** — меняет поведение лишних аргументов; допустимо.
- **Вне границ** — трейсбек на неверный диапазон git.

Записал **5 условий приёмки** и то, что сохраняем:

1. Фильтр `--types` с запятыми и пробелами.
2. Неизвестный или пустой тип → код 2, stdout пуст, git не вызывается.
3. Breaking-коммиты попадают в вывод всегда.
4. Пустой результат → только `## Unreleased`, код 0.
5. Без флага поведение прежнее.

Не меняем `parser`, `renderer`, MCP-сервер и skill.

### Шаг 3. Ревью и уточнение (слайд 9) → `evidence/03-review.md`

- **Отдельный агент-ревьюер** с промптом слайда: «Прочитай предложение и код. Проверь цель, допущения, ошибки, совместимость. Покажи конкретные пробелы. Файлы не меняй».
- Вердикт — «готово после правок», **4 существенных + 4 мелких** замечания, все приняты.

Существенные:

1. Требование «только перечисленные типы» противоречит требованию про breaking → переформулировано со ссылкой на исключение.
2. `allow_abbrev`: `--type feat` работал бы как `--types` → `allow_abbrev=False` + сценарий.
3. Раньше `--no-merges` и `--since=…` случайно работали (уходили в git); теперь код 2 → помечено **BREAKING** в proposal и Risks.
4. «Вывод не меняется» не с чем сравнить → задача 1.0: характеризационный тест.

Мелкие:

5. Повтор `--types` молча терял значение → решено объединять.
6. Ошибки argparse — `SystemExit`, «нет трейсбека» проверять через subprocess.

## 8. Вопросы и ответы

### Про задание и процесс

**— Что вы делали на практике?**
Провёл одну фичу своего проекта через полный цикл OpenSpec: explore, propose, ревью отдельным агентом, update, apply, независимая проверка, sync, archive. Потом настроил правило в config и проверил его на одном фрагменте design. В ДЗ сделал ту же работу «двумя командами» в Spec Kit и реализовал веб-сервис.

**— Почему именно `--types`?**
Это «фильтр существующего списка» со слайда 5: маленькая, но настоящая польза. В заметки о выпуске нужны `feat` и `fix`, а не `chore` и `ci`. И в ней было что обсуждать: breaking-коммиты, опечатки в типах, совместимость аргументов.

**— Какие условия приёмки?**
1. Фильтр работает с запятыми и пробелами.
2. Неизвестный или пустой тип → код 2, stdout пуст, git не вызывается.
3. Breaking-коммиты не отфильтровываются.
4. Пустой результат → только `## Unreleased`, код 0.
5. Без флага поведение прежнее.

**— Что сохраняли из старого поведения?**
Позиционный диапазон и `HEAD` по умолчанию, формат Markdown, строки `skip:` в stderr; `parser`, `renderer`, MCP-сервер, skill. Доказательство — характеризационный тест и сравнение старой и новой версий через `cmp`.

**— Что сломали и почему это нормально?**
Флаги git, которые раньше случайно проходили (`--no-merges`, `--since=…`), теперь дают код 2. Это не документированное поведение, а побочный эффект `argv[1] → git log`. Изменение помечено **BREAKING** в proposal и в Risks design. Документированный вызов `changelog-gen [RANGE]` работает как раньше.

**— Где здесь человек?**
Слайды: человек задаёт цель и принимает итог. В моём прогоне цель задал я, а одобрение спеки, приёмку фичи и принятие diff по моей договорённости фиксировал агент. Каждое решение записано с обоснованием в `evidence/`, и я их перечитал. *(Ответ честный — заранее прочитай `03-review.md`, `05-verify.md`, `02-contract-negotiation.md`, чтобы защитить каждое решение своими словами.)*

### Про OpenSpec

**— Как вы использовали OpenSpec?**
CLI — для структуры и детерминированных проверок: `init`, `new change`, `status`, `instructions`, `validate --strict`, `list`, `show`, `view`. Workflow (skills) — для работы агента: explore, propose, update, apply, sync, archive. И `config.yaml` — `context` (язык) и `rules.design` (Mermaid).

**— Что делает CLI, а что модель?**
CLI без LLM: собирает инструкцию (шаблон + указания схемы + context + rules), показывает статус и граф артефактов, проверяет структуру. Модель пишет текст и код по этой инструкции. Человек принимает. Тесты гоняет раннер (pytest).

**— Что проверяет `openspec validate --strict`, а что нет?**
Проверяет форму: SHALL/MUST в требованиях, у каждого требования есть сценарий с `####`, длина описания, `## Purpose` у новой capability, корректность дельт. **Смысл не проверяет**: противоречие между требованиями фильтра и breaking `validate` пропустил, его нашёл ревьюер.

**— Чем отличается spec в change от main spec?**
В change — **дельта** (`ADDED/MODIFIED/REMOVED/RENAMED`), описание изменения. Main spec в `openspec/specs/` — текущее поведение системы целиком. Sync сливает дельту в main spec, archive переносит change в историю.

**— Почему пустой список main specs до archive — нормально?**
Это brownfield: спек у проекта не было, первая появляется только после первого archive. Поэтому в первом change и прежнее поведение CLI записано как ADDED-требование («Выбор диапазона», «Сообщения о нераспознанных коммитах»).

**— Когда ADDED, а когда MODIFIED?**
ADDED — новое требование. MODIFIED — меняется существующее требование, и блок копируется **целиком**, со всеми сценариями, иначе при archive они потеряются. В части 2 (`--output`) MODIFIED понадобился для требования «результат в stdout».

**— Зачем design, если есть спека?**
Спека — **что** система делает (наблюдаемое поведение, без имён функций). Design — **как** (argparse или ручной разбор, где фильтровать, почему `allow_abbrev=False`). Design создаётся не всегда: только если есть технические решения, которые лучше принять до кода.

**— Что такое правило в config и как проверили, что оно работает?**
`rules.design` в `openspec/config.yaml` — указание модели для всех будущих design проекта. Проверил тремя способами:
1. `openspec instructions design --json` → правило есть в поле `rules`.
2. В `instructions specs` его нет: правило адресное.
3. Применил к тому же фрагменту: +30 строк диаграммы, 0 удалённых, смысл тот же.

**— Почему правило не изменило уже написанный design само?**
Правило попадает в **инструкцию** при генерации или обновлении артефакта. Уже существующий файл никто автоматически не переписывает, поэтому нужен `/opsx:update`.

**— Sync или archive?**
Sync обновляет main spec, change остаётся активным (например, нужна ещё доработка). Archive — финал: проверка задач и sync, перенос в `archive/дата-имя`.

**— Что было бы, если на apply выяснилось, что спека неверна?**
Остановить код, обсудить, выполнить `/opsx:update` (правка артефактов, кода не трогает), перечитать diff спеки и снова apply (слайд 10). В моём apply новых решений не понадобилось: всё было снято на ревью.

### Про конкретные шаги и код

**— Какие конкретные шаги были?**
Подготовка → explore (5 условий) → propose (4 артефакта, validate) → ревью отдельным агентом (8 замечаний) → update → apply (7 задач, сначала характеризационный тест) → независимая проверка (`cmp` старой и новой версий) → sync (main spec, 7 требований) → archive. Часть 2: propose `write-changelog-file` → сохранить фрагмент «до» → `rules.design` → `instructions design` → update фрагмента → diff +30/−0 → рендер Mermaid.

**— Зачем характеризационный тест, если есть спека?**
Спека говорит «поведение без флага не меняется», но после рефакторинга «старой версии» уже нет — сравнивать не с чем. Тест, написанный **до** рефакторинга на **старом** коде, — эталон. Он прошёл до и после без изменения ожиданий.

**— Почему `allow_abbrev=False`?**
По умолчанию argparse принимает сокращения: `--type feat` стал бы `--types`. Тогда добавить настоящий `--type` позже было бы нельзя, и это противоречит требованию «неизвестный флаг → код 2». Нашёл ревьюер, проверив в интерпретаторе.

**— Почему breaking-коммиты не фильтруются?**
Иначе `--types feat,fix` скрыл бы `refactor(api)!: drop v1` — пользователь не узнал бы о ломающем изменении. Так же поступают пресеты conventional-changelog.

**— Как проверили, что git не вызывается при неверном типе?**
Тест подменяет `cli.read_messages` функцией, которая падает при вызове. Проверяющий дополнительно запускал CLI с PATH без git: неверный тип → код 2 с ошибкой типа, а не ошибка git.
