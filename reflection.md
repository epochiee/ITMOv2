## Что сделано

- **Фича A** (ветка `feature-a`): группировка записей по типу, секции Features / Fixes / Other, пустые секции не выводятся.
- **Фича B** (worktree `../changelog-gen-b`, ветка `feature-b`): определение breaking changes по `!` и по футеру `BREAKING CHANGE:` / `BREAKING-CHANGE:`, отдельная секция Breaking Changes. CLI теперь читает полные сообщения коммитов, а не только заголовки.
- **Слияние** `feature-b` в `feature-a` (коммит `42e3ff3`): конфликты в `renderer.py` и `tests/test_renderer.py`. Итоговый порядок секций: Breaking Changes, Features, Fixes, Other. Breaking-коммит не дублируется в секции своего типа.
- **Release notes** сгенерированы skill'ом и закоммичены: `CHANGELOG.md` (`d9189fe`).

История `feature-a`:

```
d9189fe docs: add changelog for 0.1.0
42e3ff3 Merge branch 'feature-b' into feature-a
5cd5e05 feat(parser): detect breaking changes and render a separate section   (feature-b)
2d5a0e5 feat(renderer): group changelog entries by commit type
4c40e89 style: fix ruff findings in validate script and MCP server
```

Итог: 19 тестов проходят, `bash scripts/check.sh` завершается кодом 0.

## Доказательства применения

### Hook срабатывал в реальной работе агента

Три случая, во всех вывод hook вернулся агенту как blocking error:

1. **Сбой после правок фичи A.** После `Write` файлов `renderer.py` и `test_renderer.py` hook вернул 4 замечания ruff в файлах, которых агент не трогал: SIM115 в `validate.py` и I001, RUF100 ×2 в `mcp_server/server.py`. Это не мой код, а старые замечания на `main`. Агент выяснил причину, исправил их отдельным коммитом `4c40e89` и добился кода 0.
2. **Промежуточное состояние.** После `Edit` в `validate.py` hook показал оставшиеся 3 замечания в `server.py`. Это был вывод до `ruff --fix`, он пришёл с задержкой, а прямой запуск `check.sh` уже давал 0.
3. **Конфликт слияния.** Во время разрешения конфликта hook на `Write` в `renderer.py` вернул 13 ошибок `invalid-syntax`: в `test_renderer.py` ещё оставались маркеры `<<<<<<<` и `>>>>>>>`. После правки второго файла проверка прошла.

Вывод: hook ловит реальные сбои и возвращает их агенту, но он видит состояние на момент конкретного вызова, поэтому при правке нескольких файлов подряд промежуточные сбои неизбежны.

### MCP tool вызывался

- Успех: `feat(api)!: drop v1` → `{"ok": true, "type": "feat", "scope": "api", "description": "drop v1", "breaking": true}`.
- Ошибка: `update stuff` → `{"ok": false, "error": "not a Conventional Commit header: 'update stuff'"}`.
- В skill `release-notes` tool вызван для каждой из 6 тем коммитов истории: 5 распознано, 1 нет (merge-коммит).

### Skill запускался на реальной истории

Прошли все шаги `SKILL.md`: диапазон (тегов нет, взят весь `HEAD`), `parse_commit` по каждой теме, группировка по шаблону, валидатор (`OK`, код 0) и `check.sh`. Результат закоммичен в `CHANGELOG.md`.

### Ссылки на правила AGENTS.md

| Правило | Как применено |
|---|---|
| Свой regex для коммитов не писать | разбор делает `changelog_gen.parser`, в skill используется MCP tool; в renderer работа идёт с готовыми `Commit` |
| Изменение поведения сопровождать тестом | для A: 5 новых тестов в `test_renderer.py`; для B: тесты парсера, renderer и новый `test_cli.py` |
| Коммиты в формате Conventional Commits, на английском, в повелительном наклонении | все коммиты сессии (`feat(renderer): group ...`, `style: fix ...`, `docs: add ...`) |
| Работа над фичами в ветках/worktree, без прямых коммитов в `main` | `feature-a`, `feature-b` в отдельном worktree; слияние делалось между ветками, `main` не менялся |
| Python из `.venv`, «готово» = `check.sh` с кодом 0 | использовалось на каждом шаге; из-за этого же правила починены старые замечания ruff |
| Не трогать `tests/fixtures/`, не добавлять зависимости | не нарушалось |

## Трудности и находки

- **Python.** Системный pip относился к Python 3.9, пришлось создавать `.venv` на 3.12.
- **API MCP.** В `mcp` 2.x `FastMCP` переименован в `MCPServer`, документация и примеры в интернете устарели.
- **CRLF на Windows.** Мог сломать `check.sh`, это исправил `.gitattributes` (LF для `*.sh`). Для `.py` такого правила нет, и git при каждом коммите предупреждает о замене LF на CRLF.
- **Проектный MCP.** Потребовались перезапуск сессии и одобрение сервера. Явной записи об одобрении в `.claude/settings.json` нет (`enabledMcpjsonServers` отсутствует), она хранится на уровне пользователя.
- **Worktree без окружения.** В `changelog-gen-b` нет `.venv`. Решение: junction `mklink /J .venv ..\changelog-gen\.venv`; `ruff` и `pytest` через него работают.
- **Ошибка агента при правке.** Первая попытка править `parser.py` и `cli.py` скриптом Python через heredoc испортила `parser.py` (`"\n"` превратился в реальный перевод строки, смешались окончания строк), а правка `cli.py` не применилась из-за CRLF. Файл был откачен через `git checkout`, правки переделаны штатным Edit. Вывод: для файлов с CRLF надёжнее структурные инструменты правки, чем самодельные скрипты.
- **Старые замечания ruff на `main`.** По описанию задачи `check.sh` на исходном состоянии давал 0, но в этой сессии на `main` ruff находил 4 замечания в `validate.py` и `server.py`. Причина расхождения не выяснена (возможно, другая версия ruff в `.venv`). Из-за этого B, отведённая от `main`, не проходит `check.sh` целиком; после слияния всё чисто.
- **Ручной JSON-RPC тест MCP.** Ответ на ошибочный вызов не пришёл (вероятно, ввод закрылся раньше), а в реальной сессии tool сработал корректно.

## Что не доказано и ограничения

- **Hook в worktree.** Работа над B шла из сессии, открытой в основном каталоге, а hook привязан к `$CLAUDE_PROJECT_DIR`, то есть к основному каталогу. В `changelog-gen-b` он не срабатывал, там `check.sh` запускался вручную. Для доказательства нужна отдельная сессия, открытая в worktree.
- **Перечитывание AGENTS.md.** Агент не перечитывал файл в процессе работы: он уже был в контексте с начала сессии. Ссылки на правила выше — это применение правил, а не отдельные чтения файла (одно чтение было по явной просьбе в начале фичи A).
- **Breaking в реальной истории.** В истории проекта нет breaking-коммитов, поэтому секция Breaking Changes работает только на тестах; в `CHANGELOG.md` её нет.
- **Слабое место skill.** Шаблон `release-notes` не содержит секции для нераспознанных коммитов (например, merge-коммитов), валидатор проверяет только структуру файла. Нераспознанный коммит приходится указывать в отчёте, а не в файле.
- **Версия и дата.** Без тегов версию `0.1.0` пришлось взять из `pyproject.toml`.

## Выводы

1. Правила в `AGENTS.md` с чётким критерием «готово» дают агенту точку остановки: каждый шаг сверялся с `check.sh`.
2. Hook полезнее всего как «заземление»: он поймал и старые замечания, и ошибку конфликта слияния, о которых агент иначе мог не узнать до конца работы.
3. MCP-tool вместо собственного regex убирает дублирование логики разбора: один источник правды, и в коде, и в skill.
4. Skill с валидатором даёт проверяемый результат, но качество зависит от шаблона: пробелы в нём (нераспознанные коммиты) валидатор не заметит.
5. Worktree изолирует работу над фичами, но не окружение: `.venv`, hook и `$CLAUDE_PROJECT_DIR` нужно настраивать отдельно.
